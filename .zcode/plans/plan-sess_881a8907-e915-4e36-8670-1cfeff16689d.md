# 小问题 5（SenseVoice 批量解码）处置方案：查实后关闭，不做实施

## 调查结论（三条证据链）

1. **API 不存在于 Node 绑定**（计划文档前提有误）：
   - 本地安装的 sherpa-onnx-node 1.13.2：`non-streaming-asr.js` 里 `OfflineRecognizer` 只有 `createStream`/`setConfig`/`decode`/`decodeAsync`/`getResult`；原生二进制符号表（`strings sherpa-onnx.node`）无任何批量符号（`decodeOfflineStreams` 不存在）
   - npm 最新版 1.13.5：拉取发布包源码核实，同样没有 `decodeStreams`
   - `decode_streams` 是 Python/Go/C++ API；Node addon 上游（k2-fsa/sherpa-onnx）从未实现
2. **即使有也没有收益**：
   - 调用形态：转写队列每 chunk 传**单个** plan（`[plan]`，≈10s VAD 段）——单次调用内本来就只有 1 个 recognize，无批可打；跨 chunk 批量则要改动逐 chunk 的 SSE/持久化/P6 流水线 nudge 节奏，得不偿失
   - 实测基线：0.24s / 10s chunk ≈ 40× 实时（1h 视频 ≈ 86s ASR vs 6-10min LLM 润色）；P6 落地后 ASR 与 LLM 重叠，SenseVoice 永远不是长杆
   - 文档自己的触发条件「中文转写成为瓶颈时」客观未满足
3. **备选路径不划算**：依赖升级无处可升（1.13.5 也没有）；用 `decodeAsync` 做多流并行需要队列级多 chunk 批处理（SSE 延迟 + 断点粒度回归风险），估 20-40% 提速花在已可忽略的成本上
